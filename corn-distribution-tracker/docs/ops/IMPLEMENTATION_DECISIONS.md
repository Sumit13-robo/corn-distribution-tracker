# Implementation Decision Log

Record date, decision, alternatives considered, reason, effect on data/API, security impact, tests/docs updated and migration/backward-compatibility impact. Do not silently make a decision that changes stock meaning, user scope, evidence policy or status semantics.

## Decisions preset by this pack
1. Canonical inventory unit is kg, stored as decimal numeric. Display conversions are explicit.
2. Approved delivery is the point at which a distributor-to-site stock movement posts.
3. Submitted records reserve stock but do not count as verified delivery until approved.
4. Ledger movements and audit events are append-only; corrections use compensating movements.
5. Original photos are private; evidence viewing uses short-lived signed URLs.
6. Geolocation and image metadata are indicators subject to spoofing/inaccuracy, not guaranteed proof.
7. Admin first-user bootstrap is a controlled one-time operation, not public signup.
8. Initial product is single-organization; future tenant support requires explicit query-level isolation and tests.

## Implementation decisions (2026-10-22)

1. **Django + DRF replaced FastAPI + SQLAlchemy.** The URL paths and JSON response shapes in `API_CONTRACT.md` are preserved so the React client did not need a route-level rewrite. Django sessions, ORM, migrations and management commands replace the JWT/refresh flow, SQLAlchemy models, Alembic and the custom admin CLI. Alternatives considered: retaining the FastAPI backend and improving only the UI (rejected: the requested stack change), or a full API redesign (rejected: unnecessary client churn). The append-only guarantees remain database triggers; the migration and tests are Django-native.
2. **Authentication is a database-backed Django session plus CSRF.** Login sets an HttpOnly `sessionid` cookie and returns `{"user": ...}`; session restore returns the user object directly; logout deletes the server session. The SPA never stores credentials in `localStorage`. Mutating requests use the `csrftoken` cookie and `X-CSRFToken`; `/api/v1/auth/csrf` exists only for cross-origin clients that cannot read the API-origin cookie. This removes bearer access tokens and `/auth/refresh` entirely.
3. **Password-reset mail is operator-delivered in this build.** There is no mail transport. `POST /auth/forgot-password` records a request and audit event without revealing whether the account exists. An operator runs `python manage.py issue_password_reset` and supplies the one-time URL through a secure channel. The UI and CLI state this plainly rather than pretending email was sent.
4. **Invitation links are shown once to the creating admin.** Because there is no mail transport, the admin UI displays and helps copy the one-time invitation URL after creation; it is never logged and cannot be retrieved again. Invitations remain single-use, hashed at rest, expiring, and revocable.
5. **Offline drafts are user-scoped and resume by assignment.** Drafts use `corn-tracker:drafts:v1:{userId}` with the idempotency key generated once at draft creation and never regenerated on retry. Reopening the submission screen resumes the existing draft instead of creating a duplicate. States are `LOCAL_DRAFT → QUEUED → UPLOADING → SUBMITTED`; only a server record id marks a draft submitted. Failed syncs return to `QUEUED` with the error. No schema change.
6. **Evidence upload intent flow.** The client requests an intent, uploads the blob (same-origin credentials/CSRF for API calls, intent headers for presigned URLs), then submits the record with evidence intent ids. Types are restricted to JPEG/PNG/WebP with a 10 MB cap; content is sniffed server-side, SHA-256 hashed, and stored privately. Viewing uses short-lived signed URLs. Alternative: direct multipart upload in the submission request (rejected: poor offline retry and partial-failure behavior).
7. **Geodesic distance uses Vincenty inverse on WGS84 with a haversine fallback.** Distance is stored as informational review context only and is not shown as a map marker or warning. Location flags (accuracy, fix age, distance, missing GPS) are legacy and never gate approval. The only critical flags are non-location evidence-integrity checks (capture-time drift, duplicate hash, unexpected file type), which require an explicit exception reason before approval. The UI must not present any metadata as proof against spoofing.
8. **Quantity conversion is strict Decimal arithmetic at gram precision.** kg is canonical; bag conversion requires an admin-configured `kg_per_bag` and otherwise returns a 422. No silent rounding or float math. API quantities are decimal strings.
9. **Ledger integrity is database-backed.** Row locks plus unique idempotency keys guard postings; CHECK constraints encode movement-sign/type implications; corrections are compensating reversals. PostgreSQL triggers reject updates and deletes on `stock_movements` and `audit_events`.
10. **Admin CSV export is an audited read.** Export uses the same scoped queries as the analytics screens and writes an audit event. The client downloads the CSV through the authenticated session and CSRF-safe API client rather than a public URL.
11. **Map tiles are real, with an honest fallback.** The admin map uses MapLibre with OpenStreetMap streets and an Esri World Imagery satellite toggle by default, so distributor-recorded delivery points appear on real geography and exact ground detail can be checked. It intentionally plots only locations tied to submitted or approved delivery records; site reference coordinates and an admin “My location” pin are not shown. `VITE_MAP_STYLE_URL` selects another public style, while `VITE_MAP_TILE_URL` and `VITE_MAP_SATELLITE_TILE_URL` override the built-in raster templates. Attribution switches with the visible basemap. If map initialization fails (for example no WebGL), the page renders a list-first labelled coordinate board with the delivery points instead of a blank map or invented pins. OpenStreetMap and public Esri tiles are development/small-scale defaults; production must use a provider or self-hosted tiles that permit its volume.
12. **Dense admin data becomes cards on narrow screens.** `DataTable` switches to stacked cards at `≤700px` with mobile sorting; only its own wrapper is hidden by `data-table-responsive` so manually authored tables are not accidentally hidden. The admin map stays list-first on mobile. Tap targets are at least 44 px where controls are compact.
13. **Same-origin deployment shape.** A reverse proxy (the committed `apps/web/nginx.conf` is one sample) serves the built SPA and proxies `/api/` to Django, keeping the session cookie first-party. Vite build variables are the only browser-visible configuration. Local development runs native PostgreSQL, Django `runserver` and Vite; no container runtime is part of the supported workflow.
14. **Production configuration fails at Django startup.** With `APP_ENV=production`, settings validation raises `ImproperlyConfigured` for a sample/short secret, wildcard or empty hosts, insecure cookies, unsafe SameSite/secure combinations, wildcard credentialed CORS, or non-S3/missing evidence storage. Errors list field names, never secret values. Tests cover rejection and acceptance paths.
15. **Browser E2E uses a disposable Django database and session/CSRF auth.** Playwright starts the real Django and Vite processes against a dedicated `corn_tracker_e2e` database. Global setup drops/recreates it, runs Django migrations, and bootstraps the first admin; a setup project seeds campaign/site/invitation/assignment/stock through public HTTP APIs. Fixed test identities are synthetic, no real data or credentials are committed, and deleting the E2E database is the explicit reset. The suite is serial and local-only because it needs PostgreSQL with CREATEDB plus Chromium.
16. **E2E caught two cross-layer defects that unit tests missed.** (a) The distributor assignment list nested a partial site object that did not satisfy the declared `SiteOut` shape, so the endpoint returned 500 and never loaded assigned sites; the service now returns the complete site summary with an RBAC/contract regression test. (b) A captured geolocation fix was only written to the offline draft at submit, so the UI still said “no fix captured” and a reload lost it; the draft now persists the fix immediately and a component test covers it.
17. **Map accuracy in India is addressed without hiding the trade-off.** Google Maps is generally the most accurate consumer basemap in India, but embedding it requires a Google Maps API key, billing and provider terms, and no key is committed here. The app therefore provides no-key Esri satellite imagery for exact ground verification, OpenStreetMap streets for context, and exact-coordinate Google Maps links in the delivery drawer and evidence review. If an operator supplies a Google Maps key, a Google Maps JS provider can be added as a follow-up rather than pretending the OSM/Esri basemap is the same product.
17. **The 360 px check is a release gate.** Responsive fixes removed top-bar/sidebar overflow, clipped sr-only text, moved inventory balances to `DataTable` cards, clamped map fallback labels, and moved route focus/scroll so page headers are not hidden under the sticky topbar. All current routes (auth modes, 10 admin routes and the distributor routes) were screenshotted at 360 px with `scrollWidth = 360`, headings clear of the top bar, and no unexpected console errors or 5xx responses. This complements, but does not replace, real-device and assistive-technology testing.
18. **Backup and restore are one recoverable set.** The operator procedure backs up PostgreSQL and matching private evidence objects together, preserves object keys, verifies Django migration state and referenced objects, and uses an isolated restore target. A local drill against the synthetic Django E2E database passed on 2026-10-22: both migrations restored, every listed table count matched, and all referenced evidence objects were present. A production provider drill remains operator-owned.
19. **Launch risks are explicit rather than implied.** No APM/alerting, MFA, malware scanner, mail transport or automatic evidence-retention job is bundled. Rate limits are process-local. These are listed in the README known limitations and release checklist for the operator to address before broad production rollout.

## Implementation decisions (2026-10-25)

1. **Phone geolocation needs HTTPS, so the UI says so.** Browsers expose `navigator.geolocation` only in a secure context. The LAN development URL (`http://192.168.x.x:5173`) allows login and navigation but silently blocks a real GPS fix even when the site permission is “Allow”. The location hook now checks `window.isSecureContext === false` and returns explicit HTTPS guidance before calling the browser API; the HTTP origin remains useful for UI-only phone checks. Real-device capture uses an HTTPS tunnel or reverse proxy, with the exact tunnel host added to Django `ALLOWED_HOSTS`/`CSRF_TRUSTED_ORIGINS` and Vite `server.allowedHosts`. Quick tunnels are temporary/public and use synthetic demo data only.
2. **The raw evidence upload ceiling is derived from the evidence cap.** Django's default 2.5 MiB `DATA_UPLOAD_MAX_MEMORY_SIZE` caused ordinary 3–8 MB phone photos to fail with a 500 before the evidence service could validate them. Settings now derive it as `MAX_EVIDENCE_UPLOAD_BYTES + 1 MiB`; the service continues to enforce the configured cap and type/decoding checks. A 7.0 MB authenticated JPEG upload was verified as `204`, and the temporary intent/object were removed afterwards.
3. **Location never blocks approval; only non-location evidence integrity does.** The confirmed product policy is manual review from any recorded place. The backend no longer generates `GPS_MISSING`, `GPS_STALE`, `GPS_LOW_ACCURACY`, `OUTSIDE_GEOFENCE`, `EXIF_GPS_MISMATCH` or `LOCATION_EXCEPTION` for new records. `geo_status` is `PASS` with a fix and `UNAVAILABLE` without one. Distance is retained for context only when both a fix and site reference exist. Duplicate image hash, capture-time mismatch and unexpected file type remain critical and require an override reason. The distributor form and admin review label a fix **Captured** or **Missing**, never as a warning; historical location flags are filtered from the UI. The development database was reduced to the Kolhapur campaign/site, Amina's assignment and approved 1 kg record, the minimum funding ledger chain and all three user logins; Juba demo records/sites/stock and newer phone submissions were deleted after a database/private-storage backup. The retained approved record is unchanged.
4. **Sites are campaign-scoped and can start as name-only records.** The standalone admin Sites page was removed from navigation; `/sites` redirects to `/campaigns`. Campaign creation accepts optional site names in one transaction, and the selected campaign panel can add further sites or set an optional location later. `DistributionSite.campaign` is a nullable FK so legacy/global rows can be backfilled from their earliest assignment; the service enforces at most one campaign per site and rejects assigning a campaign-scoped site to a different campaign. A name-only site has null coordinates: device GPS is still stored when available, distance is null, and the delivery map does not use the site reference as a marker. Adding a location later does not rewrite historical submissions. Migration `0003` backfills existing sites from assignment campaigns; it does not invent coordinates. Tests cover campaign site creation, generated codes, duplicate names, optional location updates, cross-campaign rejection and geo evaluation without site coordinates.

5. **The admin map plots deliveries, not sites.** `/analytics/map-deliveries` returns one point per delivery record with a captured fix and status `SUBMITTED` or `APPROVED`; rejected/cancelled claims are excluded. The SPA map has no site-reference markers and no admin “My location” control, so it answers exactly where a distributor recorded a delivery. The retained approved 1 kg Kolhapur record appears even though its site is name-only. The map list is the keyboard-accessible equivalent of the markers, and selecting a record opens its site/distributor, quantity, captured coordinates/accuracy, map links and evidence-review link. Component and API tests cover the delivery-only payload, status colours, empty state and scope rejection.

## Implementation decisions (2026-10-23)

1. **Sign-in throttling counts failures, not successful sessions.** The per-IP login window (10 attempts / 5 minutes) previously consumed a slot for every request, including correct sign-ins. Repeated legitimate sign-ins from one address — common in local testing and behind NAT — could exhaust the budget and present a generic "sign-in failed" message for valid credentials. `check()` now gates before password hashing, and `record()` consumes the budget only after a failed password/nonexistent account. Other scoped limits still use the atomic `hit()`. The login screen also distinguishes `429` (with the server's retry window), `5xx`, `403`, and network failures from credential errors; credential failures remain generic to avoid account enumeration. Tests cover 13 successful logins in one window, the existing 10-failure lockout, and the locked-account retry window; browser verification confirmed the `429` message. No API shape or schema change.
